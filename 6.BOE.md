Back-of-the-envelope (BoE) calculations are one of the most important skills in a **System Design interview**. Interviewers don't expect exact numbers—they want to see if you can **estimate traffic, storage, bandwidth, and servers** so your design is realistic.

Think of it like this:

> **Requirements → Calculations → Components → Scaling**

Instead of drawing components first, you calculate the load and then decide what components are needed.

---

## Quick "Component Selection" Cheat Sheet

| Question to Ask                                       | If Answer is Yes | Add This Component                             |
| ----------------------------------------------------- | ---------------- | ---------------------------------------------- |
| Are reads much higher than writes? (>5–10×)           | Yes              | Redis cache, CDN, Read Replicas                |
| Can writes overwhelm the database?                    | Yes              | Message queue (Kafka/RabbitMQ), async workers  |
| Will a single database reach storage or write limits? | Yes              | Database sharding                              |
| Are users storing large binary files?                 | Yes              | Object storage (e.g., S3/Blob Storage)         |
| Do users need full-text search?                       | Yes              | Search engine (Elasticsearch/OpenSearch)       |
| Is the system global?                                 | Yes              | CDN, geo-routing, regional deployments         |
| Do background tasks take time?                        | Yes              | Worker service + queue                         |
| Will many clients receive live updates?               | Yes              | WebSockets or Server-Sent Events               |
| Is very low latency critical?                         | Yes              | Caching, precomputation, in-memory data stores |

## A Simple 6-Step Formula for Interviews

For almost every system design problem, follow this sequence:

1. **Estimate users** (Daily Active Users or Monthly Active Users).
2. **Convert daily operations into QPS** (Reads/sec and Writes/sec).
3. **Estimate data size** (per object, per day, per year).
4. **Estimate bandwidth** (response size × QPS).
5. **Check whether one server/database is enough**; if not, determine how many are needed.
6. **Choose components based on the bottleneck**:

   * Read bottleneck → Cache/CDN/Read Replicas
   * Write bottleneck → Queue + Workers + Sharding
   * Storage bottleneck → Object Storage + Partitioning
   * Search bottleneck → Search Engine

If you consistently perform these calculations before drawing the architecture, your design decisions will be data-driven rather than based on memorized diagrams—a key skill interviewers look for.
This is one of the most common interview discussions. The interviewer is checking whether you **choose the database based on scale**, not because "everyone uses MongoDB" or "SQL is old."

The decision should follow this path:

```text

      │
      ▼
Can one database handle it?
      │
      ├── Yes → Single Database
      │
      └── No

            ├── Need larger storage?
            ├── Need more write throughput?
            ├── Need faster reads?
            └── Need global scale?
                    │
                    ▼
      Replication / Sharding / Distributed Storage
```

## A rule many interviewers appreciate

When discussing databases, always separate **storage capacity** from **throughput**:

* **Storage capacity problem** → "The data won't fit on one machine." → Use distributed storage or shard the database.
* **Write throughput problem** → "One database can't process enough writes per second." → Shard writes across multiple databases.
* **Read throughput problem** → "One database can't serve enough read requests." → Add caches and read replicas.
* **Consistency and transactions** → Prefer a relational database.
* **Flexible schema or internet-scale horizontal growth** → Consider a NoSQL database if it fits the access pattern.

This structured reasoning is much stronger in an interview than saying, "I'd use MongoDB because it's scalable." Instead, you can justify every component with the calculations you performed.
This is exactly how experienced system designers think. They don't start with "I'll use MySQL" or "I'll use MongoDB." They first calculate the load, then decide **whether one database is enough**, and finally decide **how to distribute the data**.

# A Simple Mental Model

Whenever you perform your back-of-the-envelope calculations, ask these five questions in order:

| Question                                                                  | If Yes | Design Choice                               |
| ------------------------------------------------------------------------- | ------ | ------------------------------------------- |
| Is the data highly relational and transactional?                          | Yes    | SQL                                         |
| Does the schema change frequently or is it document-like?                 | Yes    | NoSQL                                       |
| Are the records actually large files (images/videos/PDFs)?                | Yes    | Distributed Object Storage                  |
| Can one database no longer hold the data or sustain the write throughput? | Yes    | Shard the database                          |
| Is the database overloaded mainly by reads?                               | Yes    | Add cache and read replicas before sharding |

## One final interview tip

Don't think of **SQL vs NoSQL vs Distributed Storage** as competing choices. In real systems, they almost always work together.

For example, in a photo-sharing app:

* **SQL** stores users, authentication, and billing.
* **NoSQL** stores posts, feeds, or activity data that benefits from flexible schemas or high write scalability.
* **Distributed Object Storage** stores the actual photos and videos.
* **Sharding** is a scaling technique that can be applied to **both SQL and NoSQL databases** when a single database instance can no longer meet storage or write-throughput requirements.
This is an excellent interview question because **joins are one of the biggest challenges in sharded databases**. The key idea is:

> **Sharding and joins don't work well together.** Good system design tries to **avoid cross-shard joins** rather than make them efficient.

Let's understand why.

---

# 1. First, how joins work in a single SQL database

Suppose you have two tables.

```sql
Users
-------
user_id
name

Orders
--------
order_id
user_id
amount
```

Query:

```sql
SELECT u.name, o.amount
FROM Users u
JOIN Orders o
ON u.user_id = o.user_id;
```

Inside one database:

```text
        MySQL

+----------------------+
| Users Table          |
| Orders Table         |
|                      |
| JOIN happens here    |
+----------------------+
```

The database has both tables locally, so the join is fast.

---

# 2. What happens after sharding?

```text

Shard 2

--------
```



```text

             │

             │

      Where is Order?

             │

       Shard A

             │

Need network communication
```

The database cannot perform the join locally because the data lives on different machines.

This is called a **cross-shard join**, and it is slow because it requires network communication.

---

# 3. The solution: Choose the shard key carefully

The best practice is:

> **Shard related data using the same key so related rows end up on the same shard.**

Example:

Users

```text
user_id
```

Orders

```text
order_id
user_id
```

Shard **both** tables by `user_id`.

```
hash(user_id) % 3
```

Now the layout becomes:

```text
              Router

                 │

      hash(user_id)%3

      │      │      │

      ▼      ▼      ▼

Shard1  Shard2  Shard3

Users    Users    Users

Orders   Orders   Orders
```

Example:

```
User 125
```

goes to

```
Shard 2
```

All orders for user 125 also go to

```
Shard 2
```

Now the join is local.

```text
Shard 2

Users

125

Orders

10001

10002

10003

JOIN

✓ Local
```

No network communication.

---

# 4. What if joins use different keys?

Suppose you're designing Amazon.

Tables

```
Products
Orders
Customers
```

You shard:

```
Customers

by customer_id
```

But

```
Products

by product_id
```

Now execute

```sql
Customer

JOIN

Order

JOIN

Product
```

Problem:

```text
Customer

Shard 3

-----------

Product

Shard 9

-----------

Order

Shard 5
```

Now one query needs data from three different shards.

Very expensive.

---

# 5. How real systems solve this

Instead of relying on joins, they often use **multiple strategies**.

### Strategy 1: Co-locate related data (most common)

Keep related rows together.

Example:

Uber

Everything about one rider:

```
User

Trips

Payments
```

Shard by

```
UserID
```

All user data stays together.

---

### Strategy 2: Duplicate small data (Denormalization)

Suppose

```
Products
```

are relatively small compared to orders.

Instead of joining every time:

```
Orders

order_id

product_id

product_name

price
```

Store the product name and price inside the order.

Now

```
No JOIN required.
```

This is called **denormalization**.

Storage increases a little, but reads become much faster.

---

### Strategy 3: Join in the application

Instead of SQL joining,

the application performs multiple queries.

```text
Application

     │

Get User

     │

DB1

     │

Get Orders

     │

DB2

     │

Merge in memory

     │

Return Result
```

Example:

```java
User user = userService.getUser(id);

List<Order> orders = orderService.getOrders(id);

return combine(user, orders);
```

Very common in microservices.

---

### Strategy 4: Read Models / Materialized Views

For dashboards or analytics, build a separate table.

Instead of

```
JOIN

Users

Orders

Payments

Reviews
```

Create

```
CustomerSummary
```

Already containing

```
Customer

Total Orders

Total Spend

Rating
```

One query.

No joins.

---

# 6. Example: Instagram

Tables

```
Users

Posts

Likes

Comments
```

How would you shard?

Users and Posts are frequently accessed together.

```
Shard by user_id
```

```
Shard 1

User 100

Posts

Likes

Comments
```

Everything for User 100 is together.

Fetching a profile becomes fast.

---

# 7. Example: Banking

```
Accounts

Transactions
```

Shard by

```
AccountID
```

Transactions for that account stay with the account.

Joining account and transactions is local.

---

# 8. When joins cannot be avoided

Suppose you need:

```
Top 100 selling products
```

Orders are spread across 50 shards.

Each shard computes:

```
Top products
```

Then a central service combines the partial results.

```text
Shard1

Top10

       │

Shard2

Top10

       │

Shard3

Top10

       │

Aggregator

       │

Global Top100
```

This is much more efficient than moving all rows to one place.

---

# Interview Design Rule

Think about the **most common query** first, then choose the shard key.

Example:

If the common query is:

```sql
SELECT *
FROM Users
JOIN Orders
WHERE user_id = ?
```

Shard by

```
user_id
```

If the common query is:

```sql
SELECT *
FROM Orders
WHERE merchant_id = ?
```

Shard by

```
merchant_id
```

The **shard key should match your dominant access pattern**.

---

# Decision Flow

```text
What is your most frequent query?
             │
             ▼
Which column is always in the WHERE clause?
             │
             ▼
Use that column as the shard key
             │
             ▼
Will related tables join on that column?
             │
      ┌──────┴──────┐
      │             │
     Yes            No
      │             │
Local joins     Can you:
      │          • Denormalize?
      │          • Join in application?
      │          • Build read models?
      ▼
Fast query
```

## Golden interview rule

A common beginner mistake is to say:

> "We'll shard the database and continue using SQL joins."

An interviewer will likely ask:

> "How will the join work across shards?"

A stronger answer is:

> "I would first choose a shard key that keeps related data together, making the most common joins local. For joins that still span shards, I'd avoid them where possible using denormalization, application-level composition, or precomputed read models. Cross-shard joins are expensive because they require network communication and coordination across multiple databases."

That's the answer interviewers are typically looking for.
